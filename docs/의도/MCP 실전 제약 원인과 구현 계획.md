# NAI Blue MCP 실전 제약: 원인과 구현 계획

[MCP 실전 제약과 개선 과제](MCP%20실전%20제약과%20개선%20과제.md)의 6개 항목을 코드와 2026-11-22 세션의 영수증으로 추적한 결과다. 기준 커밋 447faac. "확인"은 코드나 실행으로 본 것이고 "추정"은 측정에 맞춘 해석이다.

## 결론

- 3번(`submitted-to-inbox`)의 원인은 통로가 아니라 앱 핸들러다. 어댑터는 단계마다 3초를 기다리는데 앱은 편집 13초, 계획 10~18초, 등록 42~72초가 걸린다. 어댑터 대기를 늘리는 것만으로는 한 호출에 끝나지 않는다.
- 그 시간은 작업 크기가 아니라 쌓인 이력에 비례한다. 계획 처리 시간의 중앙값은 10월 18일까지 0.5초였고 지금은 9초다. 쓸수록 느려진다.
- 실행 이력은 정리 수단 없이 1,000건에서 모든 편집·등록을 거절한다. 지금 약 650건이다. 여섯 항목보다 이것이 먼저다.
- 4번의 `fileName: null`은 0번 job의 문제가 아니다. 공개 값 검사기가 파일명을 base64로 오인한 것이고, 같은 이름 규칙에서 4번·8번·10번 이상도 null이 된다.
- 1번과 4번의 경로 문제는 버그가 아니라 "공개 값에 로컬 경로 금지"라는 기존 규칙의 결과다. 규칙을 지키는 설계와 사용자 결정이 필요하다.
- 코드를 고치기 전에 설정 하나(`--wait-ms 20000`)로 편집과 계획의 조기 반환은 바로 줄일 수 있다.

## 실측 (2026-11-22, 영수증의 `observedAt` → 결과 파일 기록 시각)

| 명령 | 핸들러 처리 시간 | 비고 |
|---|---|---|
| `workspace.get_snapshot`, `generation.get_run`, `artifact.get_image` | 1초 안팎 | 제출부터 결과까지 0.6~1.7초 |
| `scene.patch_many` | 12.5~12.9초 (6건) | Scene 하나의 작은 수정 |
| `generation.plan` | 9.2~10.0초(2장), 18.2~18.6초(4장) | 이미지당 약 4.6초 |
| `generation.enqueue` | 42~47초(2장), 70~72초(4장) | 3 × 계획 + 약 15초에 맞는다 |
| `scene.resolve_many` | 30초 | 자체 처리는 0.2초. 앞선 등록이 끝나기를 기다렸다 |

어댑터의 단계별 대기는 `--wait-ms` 값이고 기본이 3초다(`scripts/run-agent-mcp-stdio.mjs:48,161`). 30초까지 줄 수 있는데 Pi 설정(`agent-runtime/ade-workspace/mcp-config.toml`)에는 이 인수가 없다. 같은 날 사용 기록에는 `nai-blue://requests/` 읽기 35회, 가이드 재독 14회(37,072자)가 남았다. 수동 왕복의 흔적이다.

## 항목별 원인

### 3. `submitted-to-inbox` 조기 반환

어댑터 쪽(확인)
- `generation.run`의 `waitSeconds`는 등록 뒤의 `generation.get_run` 조회(`observeRun`)에만 쓰인다. 계획·등록 단계는 `submit` → `invoke` → `inspect`가 `--wait-ms`만큼만 기다린다(`src/adapters/agent/mcp/mcp-stdio-server.ts:271,280`).
- 끝나지 않은 단계의 `hint`는 "다시 보내지 말고 영수증을 읽어라"이고(`agent-workflow-guide.ts:141`), 등록이 제출되지 않은 경우의 안내는 `generation.enqueue`를 직접 부르라는 것이다(`mcp-stdio-server.ts:286`). 그래서 에이전트가 영수증 조회와 `generation.enqueue`를 손으로 이어 붙였다.
- 같은 `requestId`를 다시 보내면 앱은 저장된 영수증을 돌려준다(`agent-command-dispatcher.ts:56-61`). 다만 지금의 재전송에는 구멍이 있다. 앱이 요청을 거절한 뒤(예: `APP_UNAVAILABLE`) 같은 ID를 다시 보내면 Python 발행기가 ready 파일을 다시 만들고(`scripts/submit-agent-mcp-command.py:155-158`), 어댑터는 남아 있는 거절 파일을 바로 돌려주는데(`scripts/inspect-agent-command.mjs:87`) 앱은 다시 올라온 요청을 실제로 처리할 수 있다. 재개 기능은 이 구멍을 막고 나서 만들어야 한다.

앱 쪽
- 실행 이력 전체 재검증(확인). `IndexedDbAgentExecutionRepository.compareAndSet`은 쓸 때마다 이력 전체를 새 Worker에서 검증하고(`src/adapters/agent/indexeddb-agent-execution-repository.ts:29,46`), 쓴 뒤 캐시를 갱신하지 않아 다음 `get`이 방금 쓴 내용을 다시 검증한다(`:19-21`). 편집 한 건의 핸들러 안에서 5회이고, 결과를 낸 직후의 승인 목록 갱신에서 한 번 더 한다(`foreground-agent-command-runtime.ts:246`). 등록은 5회 이상이고, 정산할 지난 실행이 있으면 건마다 쓰기가 따로 일어나 더 늘어난다(`agent-execution-coordinator.ts:158-166`, `:330`과 `:378`에서 두 번 호출). 검증은 레코드마다 봉투 파싱, 해시, 공개 값 검사를 한다. 이력은 영수증 기준 약 650건(편집 403, 등록 243 등)이고 회당 약 2.5초로 보인다(12.7초 ÷ 5, 추정).
- 이력 상한(확인). `agent-execution-coordinator.ts:241`은 1,000건이면 `AGENT_EXECUTION_CAPACITY`로 거절한다. 주석은 "explicit maintenance"를 말하지만 정리 기능이 없고, 이 코드를 다루는 테스트와 문서도 없다. 오늘 세션이 12건을 썼으니 같은 세션 약 29번 분량이 남았다. 10월 19일에는 하루에 220건이 쌓였다.
- 등록이 계획 준비를 세 번 한다(확인). `:375`의 `eligibility` → `ports.validate` → `rebuild`, `:315`에서 한 번 더, `:355`의 `ports.enqueue`가 `agent-scene-generation-plan.ts:266`에서 다시 한다. Queue에 실제로 들어가는 것은 그 세 번이 끝난 뒤다. 등록을 보낸 뒤 30~55초 동안은 생성이 시작도 되지 않는다.
- 계획 준비가 이력을 훑는다(논리 확인, 비중 추정). `queryVerifiedNaiGenerationCompatibility`는 이미지마다 성공한 Queue job 전체를 읽는다(`src/services/nai/verified-compatibility.ts:24,35-60`). 무작위 시드는 일치할 수 없어 끝까지 읽는다. 출력 폴더의 항목별 해시도 이미지마다 반복된다(`src/composition-root/core-runtime.ts:105-131`).
- 직렬 처리(확인). 수신함은 파일을 하나씩 처리하므로(`foreground-agent-command-runtime.ts:236-247`) 긴 핸들러 동안 읽기 요청도 기다린다.
- 시작할 때 이력의 영수증 전부를 다시 발행한다(확인, 비용은 재지 않음). `recover()`가 이력의 모든 레코드 영수증을 돌려주고 런타임이 건마다 파일로 쓴다(`agent-execution-coordinator.ts:637-642`, `foreground-agent-command-runtime.ts:197`). 그래서 예전 결과 파일의 기록 시각이 모두 11월 22일이다.
- 타이머, 잠금, 생성 완료 대기는 핸들러에 없다(확인). 창이 뒤에 있어서 느린 것도 아니다. 읽기는 1초에 끝난다.

### 4. 파일명 null과 저장 경로

- `fileName: null`(재현함). 계획 미리보기는 값이 공개 값 검사에서 거절되면 null로 바꾼다(`agent-scene-generation-plan.ts:72-76,99`). 검사기는 `[A-Za-z0-9+/_-]`가 16자 이상 이어지면 base64로 풀어 보고, 풀리면 거절한다(`src/domain/sync/payload-safety.ts`). 실제 검사기에 넣어 보니 `…draft3-1_0.png`, `_4`, `_8`, `_10`~`_99`가 거절되고 `_1`~`_3`은 통과했다. 예외는 `filenameTemplate` 키에만 있다(`:475-484`). 실제 저장에는 영향이 없다.
- `generation.get_run`을 따로 부르면 파일명이 아예 없다. 요약의 파일명은 `generation.run`이 쥐고 있는 계획에서만 온다(`mcp-result-summary.ts:57`).
- 저장 경로 미반환은 의도된 규칙이다(확인). 검사기가 `outputpath`, `savepath` 같은 키와 드라이브 문자·사용자 폴더 꼴의 문자열을 거절하고(`payload-safety.ts:24,40,538-550`), 디스패처가 결과 전체를 다시 검사한다(`agent-command-dispatcher.ts:117`).

### 5. 프리뷰 해상도

긴 변 480px 고정 PNG다(`src/services/agent/saved-artifact-image.ts:62,69`). 입력 계약은 `artifactId`뿐이고(`agent-command-input.ts:97`), 어댑터는 PNG와 1MB 이하만 통과시킨다(`run-agent-mcp-stdio.mjs:110-114`). PNG라서 480px 한 장이 base64로 약 0.5MB다.

### 1. 로컬 이미지를 `imageSource`로 쓸 수 없음

`imageSource`는 `artifactId`와 `contentChecksum`만 받는다(`agent-authoring-input.ts:47-50`). 아티팩트는 Queue가 저장할 때만 만들어지고, 입력에 절대 경로를 넣으면 `UNSAFE_PAYLOAD`다. 다만 `createArtifactRecord`는 출처 job이 없는 레코드를 이미 허용한다(`src/domain/organizer/types.ts:145-155`). 없는 것은 등록 경로뿐이다.

### 2. Precise Reference, Vibe Transfer

엔진은 지원한다. 페이로드에 `director_reference_*`와 `reference_image_multiple`이 있고(`src/services/nai/payload.ts:226-250`), Precise Reference는 V4.5만 가능하다(`model-catalog.ts:43,56`). Scene 생성은 전역 캐릭터 스토어의 레퍼런스를 쓴다(`src/lib/scene-generation/build-scene-params.ts:213,285,457-505`). Scene에 묶인 레퍼런스도, 에이전트 계약도 없다.

미확인: 사람이 앱에서 레퍼런스를 켜 두면 에이전트 계획에도 실리는가. 같은 빌더를 쓰므로 그럴 가능성이 높지만 과거 영수증에 전례가 없다(0건). 실린다면 당장 쓸 우회로이고, 동시에 에이전트 결과가 화면 상태에 따라 달라지는 문제다.

### 6. 테스트 프리셋 정리

편집 계약은 생성과 수정뿐이고, Scene 저장소 포트에 삭제 연산이 없다. 삭제는 화면 스토어의 `deletePreset`뿐이다(`src/stores/scene-store.ts:573`).

프리셋이 쌓인 까닭(추정): 기본 파일명이 `NAI_Blue_SCENE_<프리셋>_<씬>_<순번>`으로 정해져 있고 충돌 정책이 fail이라, 같은 Scene을 다시 돌리면 `output-destination-occupied`가 된다. 그래서 에이전트가 시안마다 새 프리셋을 만든다. `filenameTemplate`에 `{seed}`나 `{timestamp}`를 쓰면 같은 Scene을 반복할 수 있는데(`SceneOutputNamingEditor.tsx:75`) 가이드에 없다.

## 인사이트

1. 원인은 대기 시간이 아니라 이력 비용이다. 실행 이력, 성공한 job, 출력 폴더가 모두 정리 없이 쌓이고 호출마다 통째로 읽힌다. 통로를 고쳐도 다음 달에는 다시 느려진다.
2. ADR-016의 "한 호출로 계획·등록·대기"는 앱 처리 시간이 호스트의 60초 제한 안에 들어와야 성립한다. 앱 수정 없이는 2장도 한 호출에 끝나지 않는다(10 + 45초).
3. "다시 보내지 마라"가 재생성 금지와 재개 금지를 구분하지 않았다. 새 `requestId`로 다시 생성하는 것만 막고, 같은 `requestId`의 재호출은 재개로 안내해야 한다. 재개는 "이미 흔적이 있는 요청은 다시 발행하지 않는다"가 지켜질 때만 안전하다.
4. 경로를 숨긴 결과 에이전트가 디스크를 재귀 탐색했다. 규칙의 목적과 반대다. 원본 경로가 필요했던 까닭은 대부분 세부 검수이므로 프리뷰를 키우면 수요가 사라진다.
5. 프리뷰는 해상도보다 형식이 병목이다. JPEG로 바꾸면 1024px이 지금의 480px PNG보다 작을 수 있다(추정, 구현하며 잰다). 손가락이나 시선 확인은 전체 확대보다 부분 확대가 싸다.
6. 공개 값 검사기의 base64 추정이 긴 파일명과 부딪힌다. 파일명을 주고받는 기능(파일명 반환, 이미지 등록, `{seed}` 파일명 안내)보다 먼저 고쳐야 한다.

## 구현 계획

설정만 바꾸는 일, 어댑터만 바꾸는 일, 앱을 다시 빌드하는 일을 나눈다. 설치본 교체는 사용자가 실행하므로 앱 변경은 두 번의 빌드로 묶는다.

### 단계 0. 설정 (코드 그대로)

단계 1을 같은 날 시작했으므로 건너뛴다. 단계 1이 들어가면 필요 없다. 단계 1이 늦어질 때만 쓴다.

각 호스트의 MCP 설정에서 `run-agent-mcp-stdio.mjs` 인수에 `--wait-ms 20000`을 더하고 재연결한다. Pi는 `agent-runtime/ade-workspace/mcp-config.toml`이다.

- 효과: 편집(13초)과 계획(10~18초)이 한 호출에 돌아온다. 등록(42~72초)은 여전히 먼저 돌아오지만, `nai-blue://requests/{id}-enq` 읽기가 20초씩 기다려 주므로 조회 횟수가 줄어든다.
- 부작용: 끝나지 않은 요청을 읽으면 최대 20초 동안 응답이 없다. `generation.run`은 계획 20초 + 등록 20초까지 쓰므로 보통은 호스트 제한 60초 안이다. 뒤이은 조회가 다른 긴 요청에 밀리면 넘을 수 있고, 이것은 단계 1의 마감으로 바로잡는다.

### 단계 1. 어댑터 (앱 그대로, MCP 재연결만)

범위: `src/adapters/agent/mcp/`, `scripts/run-agent-mcp-stdio.mjs`, `scripts/inspect-agent-command.mjs`

1. 도구 호출 하나에 마감 하나를 둔다. 마감은 시작 시각 + `waitSeconds`(상한 50초)에서 마지막 응답용 5초를 뺀 값이고, 그 안의 모든 대기(계획, 등록, 조회)는 남은 시간을 0 이상의 정수로 잘라 받는다. `generation.run`이 아닌 도구는 호출 전체에 기본 20초를 준다. `artifact.get_images`처럼 여러 요청을 보내는 도구도 장마다가 아니라 호출 전체에 한 번이다. `nai-blue://requests/`, `nai-blue://capabilities`, 이미지 읽기는 지금의 짧은 대기를 그대로 둔다. 30초 상한은 `inspect-agent-command.mjs:67`과 `run-agent-mcp-stdio.mjs:49` 두 곳에 있다.
2. 다시 발행하지 않는 재개를 만든다. `invoke`는 보관된 봉투가 있으면 연결과 명령이 같은지 먼저 확인하고, 결과·거절·ready 파일 중 하나라도 있으면 서명과 발행 없이 관찰만 한다. 결과가 있으면 그 결과를, 거절이 있으면 그 거절을 돌려준다. 셋 다 없을 때(발행이 중간에 끊긴 경우)만 발행한다. 이러면 `generation.run`을 같은 `requestId`와 입력으로 다시 부를 때 끝난 단계는 저장된 결과로 지나가고 첫 미완 단계부터 이어진다. 거절된 요청은 새 `requestId`로만 다시 할 수 있다.
3. 같은 ID에 다른 입력이 오면 전용 오류로 알린다. 지금은 `invoke` 안에서 실패해 `AGENT_MCP_REQUEST_FAILED`로 뭉개지고, 미제출이라고 답하면 이미 제출된 요청을 없는 것처럼 보이게 한다. "이 ID의 기존 요청은 그대로이고 새로 제출된 것은 없다"를 말하는 코드를 따로 둔다.
4. 문구를 바꾼다. 미완 단계의 `hint`, `ENQUEUE_NOT_SUBMITTED`의 안내(`mcp-stdio-server.ts:286`), `generation.run` 설명, instructions, recovery 주제에서 "새 requestId로 다시 생성하지 않는다"와 "같은 requestId로 다시 부르면 이어진다"를 구분한다.

검증: `tests/application/agent/mcp-token-efficiency.test.ts`에 느린 가짜 수신함으로 마감(0초, 남은 시간 음수, 취소), 재개(결과 있음, 거절 있음, ready만 있음, 아무것도 없음), 다른 입력 시험을 더한다. 실제 2장 생성에서 호출 수를 센다.
기대: 앱을 고치기 전에도 생성 한 번이 `generation.run` 2~3회로 끝난다(지금 6~10회). 영수증 조회와 수동 `generation.enqueue`가 없어진다.

### 단계 2. 앱 빌드 A: 이력 비용과 파일명 (재빌드와 배포 한 번)

1. 실행 이력 검증. `compareAndSet`이 성공하면 Worker가 돌려준 사본을 얼려서 실제로 쓴 문자열과 함께 캐시에 넣는다. 더 낮은 revision으로 캐시를 덮어쓰지 않게 한다. Worker는 하나를 재사용한다. 다른 주체가 쓴 내용과 시작 시의 첫 읽기는 지금처럼 전체를 검증한다. 이것으로 쓴 직후의 재검증이 없어진다(편집 6회 → 3회).
2. 노출 정산. `refreshExposure`의 두 번 호출을 하나로 줄이고, 정산할 레코드 여러 건을 쓰기 한 번에 묶는다.
3. 실행 이력 정리. 결정 1에 따라 자동이다. 종결 레코드는 최근 200건만 온전히 두고, 그보다 오래된 것은 `requestId`·클라이언트 ID·`idempotencyKey`만 남긴 목록(최근 5,000건)으로 옮긴다. 옮기는 조건은 셋이다. 종결 상태일 것(대기·예약·불명은 남긴다). 영수증이 최종 상태로 저장됐을 것(`settle`은 이력을 먼저 바꾸고 영수증을 나중에 쓴다). 생성 레코드는 노출 정산이 끝났을 것. 식별자를 남기는 까닭은 중복 키 검사가 이력에만 있어서다(`:236-239`). 하루에 220건이 쌓인 날이 있어 날짜가 아니라 개수로 자른다. 이력을 읽는 곳(승인 목록, 복구, 취소, 저장 재시도, 화면)이 옮겨진 레코드를 필요로 하지 않는지 구현하며 하나씩 확인한다. 이미지, 아티팩트, Scene, 영수증은 건드리지 않는다.
4. 등록의 준비 횟수. 자동 경로에서 `:375`의 결과를 `execute`에 넘겨 `:315`를 건너뛴다(3회 → 2회). 등록 직전의 재검증은 남긴다.
5. 계획 준비. 성공한 job 목록을 계획당 한 번만 읽고 이미지별 해시는 집합으로 대조한다. 출력 폴더의 점유 키는 디렉터리당 한 번만 계산한다. 판정 규칙은 그대로다. 호환성 조회, 출력 폴더, 이력 검증의 구간 시간을 진단 기록에 남겨 배포 뒤 남은 비중을 본다.
6. 파일명. 검사기의 파일명 예외를 `fileName` 키로 넓힌다(경로 구분자 없음, `.png`·`.webp`, 255자 이하. 자격 증명·경로·이미지 서명 검사는 그대로). `generation.get_run`의 job에 `fileName`을 싣는다.

검증: 저장소 단위 시험(쓴 뒤 읽기가 재검증하지 않음, 외부 변경은 전체 검증, 낮은 revision이 캐시를 덮지 않음), 정리 시험(조건 넷, 정리 뒤 같은 `requestId` 재전송이 저장된 영수증을 돌려줌, 정리 뒤 같은 `idempotencyKey`가 거절됨, 상한 도달), `fileName` 0·4·8·10번 시험. 배포 뒤 같은 2장 생성으로 표의 수치를 다시 잰다.
목표(추정): 편집 3초, 2장 계획 3초, 등록 8초 이하. 이때 `generation.run` 한 호출로 2장이 끝난다. 못 미치면 구간 시간을 보고 다음 둘 중 필요한 것을 한다. 바뀐 레코드만 검증하기(전체에 걸친 `requestId` 중복·워크스페이스 검사는 남긴다), 성공 job의 해시 색인.

배포 뒤 어댑터 가이드에 반복 시안 방법을 넣는다. 같은 Scene을 고쳐 쓰고 `filenameTemplate`에 `{seed}`를 둔다. 파일명 예외보다 먼저 안내하면 null이 늘어난다.

### 단계 3. 앱 빌드 B: 검수와 입력 (계약 변경과 어댑터)

배포 순서는 앱 먼저, 어댑터 재연결 나중이다. 어댑터는 새 인수를 쓸 때만 보내서 예전 앱과도 기본 호출이 통하게 한다.

1. 프리뷰. `artifact.get_image` 입력에 `maxSide`(기본 480, 최대 1536)와 `region`(0~1 좌표의 부분 확대)을 더하고 JPEG로 인코딩한다. 어댑터의 형식·크기 검사와 `artifact.get_images`를 맞춘다. 한 호출의 장수는 바이트 합으로 제한한다.
2. 로컬 이미지 등록. 결정 3에 따라 가져오기 폴더 하나를 고정한다. 사진 폴더 바로 아래의 `NAI_Blue_Import`이고, 프리셋이나 Scene에 따라 달라지지 않는다. 입력은 파일명뿐이고, 앱이 PNG·WebP 서명, 25MB 이하, 체크섬을 확인한 뒤 `artifactId`, `contentChecksum`, 크기를 돌려준다. 편집 동의를 따른다. 경로와 이미지 바이트는 수신함을 지나지 않는다.
3. 저장 위치. `generation.get_run`에 휴대 경로(루트 종류, 세그먼트 배열, 파일명)를 싣는다. 문자열 하나로 합치면 한글 이름에서 검사기에 걸리므로 배열로 둔다. 절대 경로는 결정 2다.

### 단계 4. 레퍼런스와 정리 (3순위)

1. 레퍼런스. 먼저 미확인 항목을 `planOnly` 한 번으로 확인한다(0 Anlas). 그 뒤 Scene에 `imageSource`와 같은 꼴의 레퍼런스 결합(아티팩트 ID, 체크섬, 종류, 강도)을 더하고 계획 해시에 묶는다. Scene에 결합이 있으면 전역 상태를 물려받지 않는다.
2. 정리. 결정 4에 따라 에이전트는 프리셋을 보관만 한다. 보관한 프리셋은 스냅샷의 목록과 개수, Scene 조회, 편집 때의 전체 훑기에서 빠져야 한다. 낭비가 줄지 않는 보관은 만들지 않는다. 보관 목록은 에이전트가 따로 요청할 때만 준다.

## 결정 (2026-11-22 사용자 확정)

1. 실행 이력은 자동으로 정리한다. 이력만 줄이고 결과물은 그대로 둔다.
2. 저장 위치는 휴대 경로만 싣는다. 절대 경로는 계속 막는다.
3. 로컬 이미지는 앱이 아는 폴더와 파일명으로 등록한다. 그 폴더는 언제나 찾기 쉬운 자리 하나여야 한다.
4. 프리셋은 보관한다. 보관으로 낭비가 줄어야 하고, 보관 목록이 에이전트에게 항상 보여서는 안 된다. 삭제는 사람이 한다.
5. 포토부스보다 도구 정비가 먼저다. 단계 1과 빌드 A를 바로 시작한다. 현장 보고서가 1순위로 꼽은 로컬 이미지 등록은 파일명 예외에 기대므로 빌드 B에 둔다.

## 검토 비서(Gemini 4 Neon)의 지적과 처리

- 반영: 거절된 요청을 다시 보내면 재발행되어 뒤에서 실행될 수 있다는 지적(코드로 확인. 재개 규칙을 "흔적이 있으면 발행하지 않는다"로 바꿨다), 이력 정리가 `idempotencyKey` 중복 검사와 영수증 복구를 끊을 수 있다는 지적, 날짜 기준만으로는 상한을 못 막는다는 지적, 도구 호출 하나의 마감과 경계(0초, 음수, 읽기 자원), 다른 입력 오류가 뭉개지는 문제, `ENQUEUE_NOT_SUBMITTED` 안내, "참조가 같으면 검증 생략"을 재고 나서 하는 조건부로 미룸, `refreshExposure`의 중복, 재검증 횟수와 등록 시점 서술의 오류, `--wait-ms` 설정만으로 되는 완화, `{seed}` 안내를 파일명 예외 뒤로, 앱 빌드를 두 번으로 묶기
- 반영하지 않음: 저장된 결과를 서명 없이 읽으면 폐기·키 회전 검증이 빠진다는 지적(지금의 `nai-blue://requests/` 읽기와 같은 동작이고 앱에 새 명령이 가지 않는다. 연결·명령 일치 확인만 더했다), 단계 1을 앱 수정 뒤로 미루기(배포 없이 수동 왕복을 줄이므로 먼저 한다. 지적된 경계는 설계에 넣었다), 영수증·계획 저장소의 누적 관리(영수증은 건별 키로 읽어 지연 원인이 아니다. 아래 미확인에 수신함 폴더 누적만 남긴다)
