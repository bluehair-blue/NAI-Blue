# ADR-017: MCP 호출 마감, 재개, 실행 이력 정비

- 날짜: 2026-11-22
- 상태: 구현함. 자동 검사까지 했다. 앱 쪽 변경은 설치본에 올리지 않았고 실제 생성으로 재지 않았다
- 기반: ADR-016. 원인과 계획은 [MCP 실전 제약 원인과 구현 계획](../의도/MCP%20실전%20제약%20원인과%20구현%20계획.md)
- 범위: 어댑터(`src/adapters/agent/mcp/`, `scripts/run-agent-mcp-stdio.mjs`, `scripts/inspect-agent-command.mjs`)와 앱(실행 이력 저장소·조정자, 계획 준비, 공개 값 검사기, `generation.get_run`). 명령 입력 계약, 영수증 형식, Rust·Python은 그대로다

## 문제

2026-11-22 실전 세션에서 `scene.patch_many`, `generation.plan`, `generation.enqueue`가 매번 `submitted-to-inbox`로 돌아와 생성 한 번에 6~10회 왕복했다. 영수증으로 재 보니 앱 핸들러가 편집 13초, 계획 10~18초, 등록 42~72초였고 어댑터는 단계마다 3초만 기다렸다.

- 편집 한 건마다 실행 이력 전체(약 650건)를 새 Worker에서 5번 검증했다. 쓴 직후의 읽기가 자기가 쓴 내용을 다시 검증했다
- 실행 이력은 정리 없이 쌓이고 1,000건에서 모든 편집·등록을 거절한다
- 등록은 계획 준비를 세 번 했고, 계획 준비는 이미지마다 성공한 job 전체를 읽었다
- `generation.run`의 `waitSeconds`는 등록 뒤의 조회에만 쓰였다
- 안내 문구가 "다시 보내지 마라"뿐이라 같은 요청을 이어가는 길이 없었다
- 거절된 요청을 같은 ID로 다시 보내면 ready 파일이 다시 발행되어 앱이 뒤에서 실행할 수 있었다
- 계획 미리보기의 파일명이 공개 값 검사기의 base64 추정에 걸려 null이 됐다(순번 0, 4, 8, 10 이상)

## 결정

### 1. 도구 호출 하나에 마감 하나

마감은 시작 시각 + 예산이고 상한은 45초다(호출 상한 50초에서 마지막 응답용 5초를 뺀 값). 예산은 `generation.run`이 `waitSeconds`(기본 40초), `waitSeconds`를 준 `generation.get_run`이 그 값, 그 밖의 도구가 호출 전체에 20초다. 호출 안의 모든 수신함 대기는 남은 시간을 받는다. 남은 시간이 기본 대기(`--wait-ms`, 3초)보다 짧아도 상한이 허락하면 기본 대기만큼은 기다린다. 그래서 `waitSeconds: 0`은 예전처럼 단계마다 3초다. 자원 읽기(`nai-blue://requests/`, `capabilities`, 이미지)는 기본 대기 그대로다.

ADR-016 5절의 "`waitSeconds`는 완료 대기 시간"이 "호출 전체의 예산"으로 바뀌었다.

### 2. 흔적이 있는 요청은 다시 발행하지 않는다

`invoke`는 보관된 봉투가 있으면 연결과 명령이 같은지 확인한 뒤 기다리지 않고 한 번 본다. 결과가 있으면 그 결과를, 거절이 있으면 그 거절을 돌려준다. ready 파일이 있으면 발행하지 않고 관찰만 한다. 셋 다 없을 때만 발행한다. 앱은 답을 쓴 뒤에 ready를 치우므로, ready를 먼저 읽으면 "ready도 답도 없음"이 발행이 끊긴 경우뿐이다.

- `generation.run`을 같은 `requestId`와 입력으로 다시 부르면 끝난 단계는 저장된 결과로 지나가고 첫 미완 단계부터 이어진다. 단계 ID(`-plan`, `-enq`)가 고정이라 등록이 두 번 나가지 않는다
- 앱이 거절한 요청은 그 ID로는 끝이다. 다시 하려면 새 `requestId`를 쓴다
- 같은 ID에 다른 입력이 오면 `REQUEST_ID_INPUT_MISMATCH`를 돌려준다. 기존 요청은 그대로이고 새로 제출된 것은 없다는 뜻이며, 미제출 표시(`submissionAttempted: false`)는 싣지 않는다
- Windows에서 앱이 파일을 옮기는 순간의 읽기 실패(`EPERM`)는 20ms 간격으로 세 번까지 다시 읽는다

### 3. 문구

"결과를 모르면 다시 생성하지 않는다"를 "새 `requestId`로 다시 생성하지 않는다. 같은 호출을 같은 `requestId`와 입력으로 반복하면 이어진다"로 바꿨다. instructions의 규칙 3, `generation.run`·`generation.enqueue` 설명, 기본 가이드와 recovery 주제, 상태별 `hint`가 대상이다. 미완 단계와 `ENQUEUE_NOT_SUBMITTED`의 `hint`는 재호출을 안내한다. 고정 유입은 instructions 760자, instructions와 도구 목록 합계 8,716자다.

### 4. 실행 이력 검증

`compareAndSet`이 성공하면 검증기가 돌려준 사본을 얼려서 실제로 쓴 문자열과 함께 캐시에 넣는다. 낮은 revision은 높은 revision의 캐시를 덮지 못한다. `get`은 지금처럼 매번 저장된 바이트를 읽고, 같은 바이트일 때만 검증을 건너뛴다. Worker는 하나를 재사용하고 오류가 나면 대기 중인 요청을 모두 실패시킨 뒤 다음 호출에서 새로 만든다. 편집 한 건의 전체 검증이 6회에서 3회가 된다.

### 5. 실행 이력 정리

종결 레코드는 최근 200건만 온전히 두고, 그보다 오래된 것은 `{ requestId, clientId, idempotencyKey }`만 `compacted` 목록(최근 5,000건)으로 옮긴다. 옮기는 조건은 넷이다.

- 상태가 `completed`나 `rejected`다
- `expiresAt`이 지났다. 방금 종결된 요청의 결과 파일이 쓰이기 전에 옮겨지는 일을 막는다
- 저장된 영수증이 최종 상태이고 결과가 같다
- 승인된 생성 레코드는 노출 정산이 끝났다

레코드가 300건을 넘을 때 새 요청을 받기 전에 한 번의 쓰기로 한다. 정리가 실패해도 그 요청의 결과에는 영향이 없다. `requestId` 중복과 `(clientId, idempotencyKey)` 중복 검사는 `compacted` 목록도 본다. 1,000건 상한은 정리할 수 없는 레코드가 쌓일 때의 안전장치로 남는다.

이력 형식은 `compacted`가 생길 때 `schemaVersion` 2가 된다. 그 전까지는 버전 1 바이트 그대로다. 버전 2 이력은 이전 빌드가 읽지 못한다.

이력을 읽는 곳은 조정자뿐이고(승인 목록, 복구, 승인·거절, 취소·저장 재시도, 노출 정산), 모두 종결되지 않은 레코드나 정산 전 레코드만 본다. 이미지, 아티팩트, Scene, 영수증은 건드리지 않는다.

### 6. 등록의 준비와 노출 정산

자동 등록은 핸들러의 적격성 결과를 `execute`에 넘겨 다시 계산하지 않는다(계획 준비 3회 → 2회). 정책이나 동의가 그사이 달라졌으면 다시 계산한다. Queue에 넣기 직전의 재구성과 비교는 그대로다. 사람 승인 경로는 바뀌지 않았다. 노출 정산은 여러 건을 쓰기 한 번에 묶고, 자동 경로에서 두 번 하던 것을 한 번만 한다.

### 7. 계획 준비

호환성 조회는 계획의 이미지 전부를 받아 성공한 job 목록을 한 번만 읽는다. 이미지별 결과는 단일 조회와 같다(목록 순서로 처음 검증된 job이 이긴다. 읽기 실패는 아무것도 인정하지 않는다). 출력 폴더의 점유 키는 디렉터리당 한 번만 계산한다. 점유 집합은 같다. `agent-plan:scene-preparation`, `agent-plan:compatibility-scan`, `agent-plan:output-planning` 구간을 User Timing으로 남긴다.

### 8. 파일명

검사기는 `fileName` 키의 값이 맨 파일명일 때만 base64·hex 추정을 건너뛴다. 조건은 255자 이하, 경로 구분자·`:`·`..` 없음, `.png`나 `.webp`로 끝남이다. 자격 증명, 경로, 이미지 서명 검사는 그대로다. `generation.get_run`의 job 행은 저장이 끝나면 `fileName`을 싣고(job의 출력 예약에서 온다. 추가 읽기 없음), 어댑터 요약의 `artifacts`가 그것을 쓴다. 계획을 쥐고 있지 않은 `generation.get_run`에서도 파일명이 나온다.

## 검토 비서(Gemini 4 Neon)의 지적과 처리

계획 단계의 지적은 계획 문서에 있다. 구현을 마친 뒤 diff를 보였다.

- 반영: 이력 정리가 상한에서 다시 돌지 않는 경로(정리하고도 남은 레코드가 900건을 넘으면 다음 정리 시점이 상한 위로 잡혔다. 시점을 상한 이하로 묶고, 상한에 닿으면 한 번 강제로 정리한 뒤 다시 받는다), 쓰기에 성공한 뒤의 레코드 수 갱신, Worker 오류 때 대기 중인 요청을 먼저 실패시키고 나서 종료하기, Worker 쪽 역직렬화 오류 전달, 단계 대기의 상한 클램프, 서명과 발행에 쓴 시간을 관찰 대기에서 빼기, 파일명 예외에서 `+`·`=`·제어 문자 제외, 구간 계측 헬퍼를 하나로 합치고 이력 검증 구간 더하기
- 반영하지 않음: 단계 대기의 기본 대기 하한을 없애기(하한은 예전 동작을 지키려는 것이고 45초 상한 안에서만 작동한다), 적격성 결과를 재사용할 때의 만료·인가 재확인(예약 쓰기 안과 예약 직후에 이미 다시 확인한다), 마감 계산을 단조 시계로 바꾸기(상한 클램프로 막았다), 출력이 하위 폴더에 놓일 때의 파일명(단일 job 조회와 같은 규칙으로 둔다), `compacted` 5,000건 밖의 `idempotencyKey`(의도한 상한이다), 구간 시간의 영속 기록(프로파일에서 본다)

## 바꾸지 않은 것

- 요청 서명, 수신함 파일 흐름, 영수증 저장과 재생, 실행 중인 앱의 해시 확인
- 명령 입력 계약과 영수증 형식. Rust와 Python
- 승인·예산·revision·호환성 판정 규칙, 예약 뒤 등록의 순서, 정확한 계획 ID·해시 비교
- 실행 이력 검증 규칙. 워커와 비워커 경로가 같은 파서를 쓴다

## 검증

- 전체 테스트 2,898개 통과(4개 건너뜀), 런타임 가드 테스트 7개, 타입 검사, 린트, 구조 검사, 의존성 검사 통과
- 새 시험: 호출 마감(`mcp-token-efficiency.test.ts`), 재발행 없는 재개(`mcp-request-resume.test.ts`), 캐시와 Worker 재사용(`agent-ledger-cache.test.ts`), 이력 정리(`agent-ledger-compaction.test.ts`), 호환성 일괄 조회, 출력 점유 키, 파일명 예외, job 행의 파일명
- `agent-mcp-stdio-process.test.ts`의 프로세스 종료 시험은 전체 실행 세 번 중 두 번 실패하고 단독으로는 세 번 모두 통과했다. 변경 전 커밋의 전체 실행에서도 같은 시험이 실패했다. ADR-016에 적힌 불안정 시험이다
- 하지 않은 것: 설치본 교체, 실제 생성으로 처리 시간 다시 재기, 실제 이력(약 650건)의 첫 정리, 실제 Python 발행기와 호스트(Pi, Codex, Claude Code)에서의 재개

## 알려진 한계

- 버전 2 이력은 이전 빌드가 읽지 못한다. 설치본을 예전 빌드로 되돌리면 에이전트 명령이 `INVALID_EXECUTION_STORE`가 된다
- 쓰기마다의 전체 검증은 남는다(편집 한 건에 3회). 이력이 200~300건으로 줄어 회당 비용도 줄지만 재지 않았다. 모자라면 바뀐 레코드만 검증하는 방법과 성공 job의 해시 색인을 한다
- `expiresAt`(제출 뒤 1시간)이 지나지 않은 레코드는 정리되지 않는다. 한 시간에 800건 넘게 쌓이면 상한에 닿는다
- 수신함 폴더의 파일은 여전히 쌓인다
- `generation.get_run`의 파일명은 출력이 하위 폴더에 놓이면 빠진다
