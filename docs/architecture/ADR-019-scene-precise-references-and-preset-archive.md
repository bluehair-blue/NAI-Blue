# ADR-019: Scene의 Precise Reference 결합과 프리셋 보관

- 날짜: 2026-11-22
- 상태: 구현했다. 자동 검사와 개발 서버 화면 확인까지 했고 설치본에는 올리지 않았다
- 기반: ADR-018. 범위와 완료 기준은 [MCP 실전 제약 원인과 구현 계획](../의도/MCP%20실전%20제약%20원인과%20구현%20계획.md)의 단계 4
- 범위: Scene 데이터 모델과 저장소, 편집 계약(`scene.patch_many`), Scene 파라미터 조립, 프리셋 목록과 관리 창, 스냅샷·조회·계획, 어댑터 안내

## 문제

- Scene 생성은 화면에서 켠 전역 캐릭터 레퍼런스만 썼다. 에이전트의 Scene이 화면 상태를 그대로 물려받았고, 캐릭터마다 다른 레퍼런스가 필요한 작업(PPP 포토부스)에서 Scene마다 레퍼런스를 줄 수 없었다
- 에이전트가 시안마다 만든 프리셋이 쌓였고(328개), 숨기거나 정리할 수단이 없었다

## 결정

### 1. Scene의 Precise Reference

Scene에 `preciseReferences`를 더했다. 항목은 `{ artifactId, contentChecksum, referenceType, strength, fidelity }`이고 최대 10개다(화면에서 켤 수 있는 수와 같다). `referenceType`은 `character`, `style`, `character&style`이다.

- 필드가 없으면 지금처럼 전역 상태를 물려받는다. `null`이나 빈 목록이면 레퍼런스 없음이고 물려받지 않는다. 목록이면 그 목록만 쓴다. `imageSource`와 같은 세 상태다
- Vibe Transfer는 다루지 않는다. 어느 상태에서도 전역 상태를 따른다
- `scene.patch_many`가 목록이나 `null`을 받고, 저장 전에 아티팩트 레코드·체크섬·형식·크기를 확인한다. `scene.resolve_many`가 묶인 내용을 보여 준다. 이미지 바이트는 오가지 않는다
- 생성할 때 저장된 원본을 체크섬으로 확인해 읽고, 전역 레퍼런스가 지나는 것과 같은 자원 경로에 넣는다. 그래서 계획 해시가 레퍼런스의 내용과 값에 묶이고, 내구성 Queue의 자원 보관도 같은 방식으로 된다
- Precise Reference가 없는 모델(V5)의 Scene에 묶으면 계획이 모델 사유로 거절된다
- 레퍼런스 이미지는 생성 결과이거나 `artifact.import`로 등록한 이미지다
- 필드가 없는 Scene은 전과 같은 바이트로 저장된다. 기존 데이터를 옮기지 않는다

### 2. 프리셋 보관

프리셋 껍데기에 `archivedAt`(보관한 시각)을 둔다. Scene 문서, 리비전, 결과 링크, 결과 이미지는 보관과 복원으로 바뀌지 않는다. 보관하지 않은 프리셋은 전과 같은 바이트로 저장된다.

- 묶음: 보관은 하위 폴더를 모두 함께 숨긴다. 기본 프리셋은 보관하지 않는다. 먼저 보관해 둔 하위 폴더는 자기 시각을 지킨다. 복원은 같은 동작으로 보관한 하위 폴더(같은 시각)와 보관된 상위 폴더를 함께 되살린다. 보던 프리셋이 보관되면 기본 프리셋으로 옮긴다
- 에이전트: `scene.patch_many`의 `presetArchived`가 `true`면 보관, `false`면 복원이다. 이 필드만 있으면 `changes`가 비어도 된다. Scene을 바꾸지 않는 요청은 리비전을 올리지 않는다. 편집 동의와 승인은 다른 편집과 같은 흐름을 탄다. 삭제는 사람만 한다
- 거절: 보관된 프리셋의 Scene 편집은 `AGENT_PRESET_ARCHIVED`다(같은 요청에서 복원하면 받는다). 기본 프리셋의 보관은 `AGENT_PRESET_NOT_ARCHIVABLE`이다
- 에이전트에게 숨김: 스냅샷의 프리셋·Scene 목록과 개수에서 빠지고 `totalArchivedPresets`만 남는다. 보관 목록은 `include: ["archived"]`로 요청할 때만 나온다. `scene.resolve_many`는 `found: false, archived: true`로 답한다. 계획은 `scene-preset-archived`와 `restore-preset`으로 거절되고, `production.create`는 `AGENT_PRESET_ARCHIVED`다. 계획한 뒤에 보관하면 등록이 충돌로 끝난다
- 사람 화면: Scene 화면의 프리셋 목록, 폴더 작업대, 작업 기록에서 숨는다. 프리셋 관리 창에 '선택 폴더 보관'이 생겼고, 목록 아래 접힌 '보관함 (N)'에서 행마다 복원과 삭제를 한다. 삭제는 확인을 거쳐 휴지통으로 간다. 에이전트의 보관·복원 승인 카드는 함께 바뀌는 폴더 수를 보여 준다
- 복제는 보관된 하위 폴더를 복사하지 않는다

### 3. 훑기 줄이기

편집 요청은 Scene 권한 런타임에 화면 편집을 먼저 비우게 하고, 그때 프리셋마다 Scene을 다시 투영해 해시를 냈다(328개 프리셋, 3,262개 Scene). 이제 투영 결과를 프리셋의 Scene 배열 참조로 기억하고, 같은 배열·같은 권한 문서·같은 결과 링크 상태면 해시를 다시 쓴다.

- 근거: 스토어는 Scene 배열을 고쳐 쓰지 않고 새로 만든다. 권한 문서는 교체만 된다. 결과 링크를 관리하는 ID 집합은 투영 안에서만 늘고, 늘 때마다 센다
- 현재 리비전 상태와의 비교는 매번 한다. 생략되는 것은 투영과 해시 계산뿐이다
- 보관한 프리셋만이 아니라 바뀌지 않은 프리셋 전부가 훑기에서 빠진다. 저장 구조는 그대로다

## 어댑터가 예전 앱과 통신하는 동안

- `presetArchived`, `preciseReferences`, `includeArchived`는 쓸 때만 보낸다. 쓰지 않는 호출은 예전 앱에서도 된다
- 예전 앱이 이 필드를 거절하면 어댑터가 앱 갱신 안내를 붙인다. 입력은 어댑터가 같은 계약으로 먼저 검사하므로, 앱이 입력 오류로 거절하면 계약이 예전 것이다
- 예전 앱의 `scene.patch_many`, `workspace.get_snapshot` 스키마 해시를 받아들인다

## 검토 비서(Gemini 4 Neon)의 지적과 처리

코드에서 확인한 뒤 처리했다. 수정분은 다시 검토받지 않았다.

- 반영
  - 보관만 하는 요청의 복구가 삭제된 프리셋을 "복원 완료"로 읽는다 → 프리셋이 있는지 먼저 본다
  - 도구 목록은 `preciseReferences`의 빈 목록을 받는다고 알리는데 계약은 거절한다 → 빈 목록도 "없음"으로 받는다
  - 승인 카드가 함께 보관·복원되는 폴더를 알리지 않는다 → 그 수를 보여 준다
  - 관리 창이 열린 채 에이전트가 선택된 폴더를 보관하면 보이지 않는 폴더가 선택에 남는다 → 선택을 보이는 폴더로 거른다
  - 오래된 데이터의 `parentId` 순환이 보관되면 보관함에 행이 없고, 휴지통 이동의 상위 탐색이 끝나지 않는다 → 순환마다 한 행을 두고 탐색에 방문 표시를 넣었다
  - 예전 앱 안내가 `preciseReferences`를 빼놓는다 → 넣었다
  - 기본 스냅샷도 보관 목록을 만든다, 휴지통 이동을 연달아 누르면 두 번 들어간다 → 요청할 때만 만들고, 진행 중에는 다시 받지 않는다
- 반영하지 않음
  - 훑기 캐시가 결과 링크 ID 집합의 바깥 변경을 놓친다: 그 집합은 시작할 때 만들어지고 투영 안에서만 늘며 늘 때마다 센다. 바깥에서 고치는 코드가 없다
  - 보관만 하는 요청의 복구가 우연히 같은 상태를 완료로 읽는다: 요청이 바란 상태와 지금 상태가 같다. 상태를 정하는 요청이라 결과가 같다
  - 구 데이터에서 기본 프리셋이 보관되는 폴더 아래에 있는 경우: 지금 코드로는 기본 프리셋을 다른 폴더 아래로 옮길 수 없다. 그런 데이터에서도 기본 프리셋은 보이고 쓸 수 있다
  - 먼저 보관한 하위 폴더가 상위 행의 개수에 합쳐 보인다: 삭제 확인의 개수는 실제 삭제와 같다. 복원 뒤 그 하위 폴더는 자기 행으로 남는다(아래 한계)

## 바꾸지 않은 것

- Scene 저장분의 구조, 영수증 형식, 명령 이름 목록(Rust와 Python은 그대로다)
- 예상 Anlas 계산. 레퍼런스를 계산에 넣지 않는 것은 전역 레퍼런스도 같다

## 검증

- 자동 검사: `npx vitest run` 2,970개 통과(건너뜀 4), `tsc --noEmit`, eslint, dependency-cruiser, knip, `node --test tests/scripts/agent-runtime-guard.test.mjs` 통과
- 화면: 개발 서버(빈 데이터, 설치본 아님)에서 프리셋 관리 창을 열어 폴더와 하위 폴더를 만들고 보관 → 목록에서 사라지고 '보관함 (1)'이 생김 → 펼치면 "폴더 2개 · 씬 0개"와 복원·삭제 → 삭제 확인과 취소 → 복원하면 하위 폴더와 함께 돌아옴을 확인했다. 보관한 뒤 Scene 화면의 프리셋 목록에 기본 프리셋만 남는 것도 봤다
  - 이 확인에서 창이 낮으면(1280×800) 보관함이 목록 아래로 잘려 보이지 않는 배치 결함을 찾아 고쳤다. 폴더 열이 통째로 스크롤되고, 펼친 행과 삭제 확인이 보이는 자리로 온다
- 하지 않은 것: 설치본 확인, 실제 작업 공간(프리셋 328개)에서의 처리 시간, Precise Reference를 묶은 실제 생성, 보관함에서 휴지통으로 보내는 동작의 화면 확인

## 알려진 한계

- 예상 Anlas가 Precise Reference를 반영하지 않는다. NovelAI가 따로 과금하면 실제 소모가 예상과 예산 상한보다 클 수 있다
- 레퍼런스나 Image2Image 입력으로 쓰는 원본 파일을 지우면 그 Scene의 계획이 실패한다. 파일을 되돌리면 다시 된다
- Vibe Transfer는 Scene에 묶을 수 없다
- 보관함의 행은 보관된 가지 전체의 개수를 보여 준다. 먼저 따로 보관한 하위 폴더가 그 안에 있으면 복원 때 돌아오는 수는 그보다 적고, 그 하위 폴더는 보관함에 자기 행으로 남는다
- 활성 폴더를 지우면 그 아래 보관된 하위 폴더도 함께 휴지통으로 간다. 삭제 확인의 개수에는 들어 있다
- 보관된 폴더를 휴지통에서 되살리면 보관된 상태로 돌아온다
- 생산 요청을 만든 뒤 그 프리셋을 보관하면 `production.plan_next`가 보관이 원인임을 알리지 않고 실패한다(코드로 본 것이고 응답 형태는 확인하지 않았다)
