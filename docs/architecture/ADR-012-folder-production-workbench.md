# ADR-012: 폴더 중심 에셋 작업대 — 1단계

- 날짜: 2026-09-07
- 상태: 구현. 브라우저 및 자동 검증 범위는 아래에 기록한다.
- 요구 자료: `docs/local/plans/NAI_Blue_Folder_to_CDN_Brief.md`
- 범위: 폴더 작업면, 서로 다른 프롬프트의 일괄 입력, 저장되는 생산 수량, 기존 실행 계획의 출력 경로 미리보기.

## 제품 완료 기준 정정 — 2026-09-08

위 상태는 첫 UI 구현 범위의 상태다. 사용자 요구인 **전용 에이전트 도구로
생성 데이터를 설정하고 실제 대기열에 등록한 결과를 프론트엔드에서 보는
전체 사용 흐름은 아직 미완료**다. GUI 조작을 에이전트 지원의 대체 경로나
완료 근거로 계산하지 않는다. 화면 조작은 UI 검증 수단으로만 사용한다.

원 요구 문서 1절·6절은 GUI와 외부 에이전트가 같은 폴더 데이터와
조회·계획·실행 기능을 사용하고, 변경 및 진행을 같은 화면에 반영하도록
이미 요구했다. 새 기획을 사용자에게 요구하지 않는다.

다음 구현의 우선 완료 단위는 아래 한 흐름이다.

1. Codex가 전용 도구로 현재 생성 데이터와 폴더를 읽고, 사용자 지시에 따라
   항목별 프롬프트·생성 파라미터·장수·파일명·지정 저장 경로·R2 업로드 여부와
   연결·폴더를 설정한다. 기존 Scene/Folder 저장소와 application 검증을 사용한다.
2. 변경 결과는 사람이 보는 동일한 저장 데이터에 반영된다. 별도 임시 파일을
   사용자가 가져오거나 화면에 재입력해야 하는 경로를 완료로 보지 않는다.
3. 확정 대상·수량·목적지·비용 범위의 계획을 기존 실행 정책에 따라 검토하고,
   기존 durable Queue에 실제 등록한다. 파일 제출이나 계획 생성만으로
   대기열 등록 성공을 보고하지 않는다. 실제 run/batch/job 식별자로 확인한다.
4. 기존 실행기가 생성·저장을 수행하고, 프론트엔드는 같은 작업의 대기·생성 중·
   완료·실패 및 실제 생성 프리뷰를 자동 반영한다. 새로 생성한 결과가 해당
   항목에 연결되어야 한다. R2를 켠 경우에는 저장 후 업로드 상태도 연결한다.
5. 같은 요청 재전달과 앱 재시작에서 중복 등록·중복 생성 없이 기존 작업을
   다시 확인한다. 비용과 공개 범위가 달라지면 기존 정책대로 재검토한다.

정정 당시 단절 지점은 UI 작업대의 Scene/Folder 편집, 별도 파일 기반 편집,
기존 workflow-draft만 입력받는 MCP 계획/실행 인터페이스 사이에 있다.
MCP는 폴더·생성 항목 준비 기능과 충분한 조회 계약이 부족하고 실제 Codex
호스트 연결도 검증되지 않았다. 기존 Queue·출력 저장·Artifact 연결을
재사용하여 이 경로를 먼저 완주한 뒤 대량 묶음 실행과 편집 범위를 확장한다.

첫 완료 증거는 실제 Codex의 도구 호출 → 서로 다른 설명과 지정 파라미터의
영구 저장 → 실제 Queue 등록 → 승인된 생성 실행 → NAI Blue의 해당 항목에
실제 결과 프리뷰 표시다. 모의 Provider, 테스트 이미지, UI 자동 조작,
독립 기능 테스트는 이 전체 흐름의 실제 실행 증거와 구분해 보고한다.

2026-09-08 후속 구현은 [ADR-013](ADR-013-agent-folder-production.md)에 기록한다.
전용 MCP의 Scene/Folder 편집과 기존 Queue 등록, 화면 진행 상태 및 Artifact 프리뷰를
연결했다. 공식 SDK와 실제 저장/대기열/프리뷰 코드를 사용한 자동 검증이 있지만,
현재 Codex 호스트 등록과 실제 Provider 생성까지 완료했다는 의미는 아니다.

## 사용 흐름

기본 진입점은 `/folders`다. 빈 폴더에서는 프롬프트를 바로 입력한다. `다음 · 수량과 저장 확인`으로 항목을 저장하면 추가한 항목만 선택되고, 수량과 저장 위치 확인 → 생성 전 검토 → 기존 Queue 승인으로 이어진다. 상단 탐색은 글자가 보이는 `에셋 만들기 / 진행 상황 / 도구`로 구성한다. Guided와 기존 Scene 편집기는 도구 메뉴에서 접근한다.

- 첫 화면에는 직접 입력 폼을 표시한다. 이름 생략 시 `asset_001`처럼 자동으로 채우고, 수량은 1장부터 시작한다. 다른 프롬프트를 추가하는 버튼과 표 붙여넣기를 함께 제공한다. 입력 방식 전환은 각 초안을 보존한다.
- 비어 있는 폴더에는 검색·선택·페이지 이동·생성 실행 버튼을 표시하지 않는다. 항목이 생기면 에셋별 수량과 다음 행동을 먼저 보여주고, 검색·일괄 편집 및 상세 저장 설정은 펼쳐서 사용한다.
- 가져온 프리셋의 저장된 ID를 확인한 뒤 그 ID만 선택한다. 새로 가져온 프리셋을 목록 앞에 표시해 방금 추가한 에셋을 다음 단계에서 바로 확인할 수 있게 한다. 기존 에셋은 자동으로 생성 대상에 포함하지 않는다.

- 생성 폴더 ID를 가진 항목을 Scene 프리셋 전체에서 모아 표시한다. `모든 폴더`, `폴더 미지정`, 선택 폴더, 명시적 하위 폴더 포함을 지원한다. 기존 수동 출력 항목을 기본 폴더에 임의로 연결하지 않는다.
- 검색 결과 전체 선택은 실제 항목 ID 집합을 저장한다. 실행 대상은 현재 검색 결과와 선택 ID의 교집합이다. 검색 밖의 선택은 실행에서 제외한다고 표시한다.
- 목록과 썸네일은 페이지당 60개만 렌더링한다. 폴더별 검색, 선택, 보기, 페이지 및 스크롤은 화면에 머무는 동안 복구한다. 영구 작업 상태와 UI 탐색 상태를 혼합하지 않는다.
- 표 붙여넣기는 탭으로 구분한 `이름 / 프롬프트 / 수량 / 파일명 템플릿(선택)`을 지원한다. 쉼표는 프롬프트 내용이다. 수량 생략은 1, 유효 범위는 1–999, 입력 항목은 최대 2,400개다. 다중 줄 인용 CSV는 지원하지 않는다. 한국어/영어 이름·프롬프트 헤더는 생략 가능하다.
- 기존 Scene 폴더의 기본 템플릿을 선택하면 생성 설정, 공통·네거티브·캐릭터 설정을 복사하고 행별 프롬프트를 추가한다. 결과 이미지나 원격 배포 연결은 복사하지 않는다.

## 데이터와 실행 소유권

새 폴더 저장소나 별도 dispatcher는 만들지 않는다. 생성 폴더 변경은 기존 설정 저장소 → 폴더 application 계획 → repository 경로를 이용한다. 표시 이름과 경로 이름의 기존 분리, 폴더 해석, 상속 규칙을 유지한다.

새 항목은 기존 표준 ScenePreset import 한 번으로 추가한다. `flushSceneAuthorityRuntime()`은 기존 runtime의 commit 대기를 노출하며, 성공 전 repository에서 추가한 ID 전부를 다시 확인한다. 저장 결과가 불확실하면 다시 import하지 않는다.

`SceneAuthoringRecord.productionCount?: number`는 반복 제작 시 사용할 수량이며 1–999 정수다. 같은 선택의 대량 수량 편집은 한 번의 store 갱신으로 반영한다. 이 값은 repository에 저장되고 재시작 후 유지된다. 기존 문서는 이 필드 없이 유효하다. `queueCount` 및 개별 대기열 파일명은 기존처럼 임시 상태이며 재시작 때 복구할 실행 목록으로 사용하지 않는다. 작업대의 추가 직후에는 pending Queue 항목을 만들지 않는다.

계획과 실행은 `prepareSceneQueueReview` / `enqueueReviewedSceneQueue`를 사용한다. 대상 preset ID, scene ID, 수량과 기존 명시적 파일명을 전달한다. 비용 검토, revision 재검증, 원자적 전체 출력 파일 예약, 불확실한 Provider 결과의 기존 복구 규칙을 그대로 사용한다. 승인된 실행은 기존 대기열에서 확인한다.

## 파일명, 로컬 위치, R2 키와 URL

파일명은 기존 Scene planner가 계산한다. 로컬 표시 경로는 실제 출력 할당기가 해석한 directory와 할당된 filename에서 얻는다. 이 경로는 일시적인 GUI 정보이며 durable reservation에 추가하지 않는다.

R2 키는 동일한 실행 계획의 `planR2Release` 결과다. profile/folder prefix를 화면에서 다시 붙이지 않는다. 충돌 정책이 `suffix`일 때의 실제 계획 키도 그대로 보여준다. 공개 URL 문자열은 계획에 연결된 공개 기본 주소와 확정 키를 사용해 경로 요소마다 인코딩한다. private 또는 유효한 공개 주소가 없는 연결에는 URL을 만들지 않는다.

실행 검토에서 25개씩 전체 파일명·최종 프롬프트·로컬 경로·R2 키·예정 URL을 확인하고 전체 계획 JSON을 복사할 수 있다. JSON은 `status: planned`, `publicAccessVerified: false`를 명시한다. 이것은 업로드 완료 목록이나 공개 접근 확인 결과가 아니다.

## 이번 단계의 경계

- 2,400개는 입력·화면 조작 검증 규모다. 현재 측정된 Windows Queue 한도인 실행당 100장 / 출력 파일 400개를 높이지 않는다. 한도를 넘는 선택에는 실행 전 안내를 표시한다. 미측정 브라우저 환경의 생성 실행도 열지 않는다.
- 수천 장의 자동 분할 제출, 예약 번호 이어쓰기, `{expression}` / `{index:03}` 새 변수, 새 프롬프트 상속 정책, 전체 생성 폴더 복제, 기존 공개 URL 교체·캐시 무효화, 업로드된 URL의 공개 접근 검사는 후속 단계다. MCP 폴더 생성/편집은 ADR-013에서 구현한다.
- 직접 경로와 상태가 보이는 GUI 및 계획 JSON을 제공하지만 실제 외부 에이전트가 새 폴더 명령으로 실행한 증거는 아니다.
- 실제 NovelAI 호출, 실제 R2 업로드·공개, 설치 앱 교체, crash/device 검증을 이번 자동 검증에 포함하지 않는다.

- `tests/presentation/workflow/folder-workbench.test.ts`: 서로 다른 프롬프트의 2,400개 입력, 복사 독립성, 폴더 범위, 한 번의 수량 갱신, pending Queue 불변.
- `tests/lib/scene-authority-runtime.test.ts`: 생산 수량 저장·재시작 복원과 임시 대기열 초기화.
- `tests/services/queue/scene-queue-r2-planning.test.ts`, `tests/composition-root/core-runtime-output-planning.test.ts`, `tests/domain/r2/public-url.test.ts`: 기존 계획의 실제 할당 경로·키와 공개 URL 문자열.
- `scripts/qa-folder-workbench.mjs`: 독립 브라우저에서 표 추가·재시작, 2,400개 검색/선택/수량 편집/페이지 이동, 목록·썸네일 및 390px/1440px 화면을 검증한다. Provider 호출이나 Queue 승인 없이 수행한다. 증거는 ignored `artifacts/folder-workbench/`에 쓴다.
- 기존 전체 Vitest, ESLint, TypeScript/Vite build와 architecture check를 함께 실행한다.

2026-09-07 최초 구현 검증 결과: 전체 Vitest **2,450 통과 / 4 건너뜀 / 실패 0**, ESLint 및 TypeScript/Vite build 통과, architecture check 위반 0. 브라우저 검사 **9/9 통과**, uncaught page error 0. 붙여넣기 3개 항목의 수량 `3/2/1` 및 일괄 편집 수량이 새로고침 후 유지됐다. 2,400개 자료에서 검색 결과 1,200개 선택 → 각 3장 → 3,600장 계획 수량 표시, 다른 검색에서 대상 0개, 폴더 복귀 시 선택 복원, 최대 60개 DOM 항목과 390px/1440px 화면의 조작을 확인했다. 이 수량 표시는 실제 3,600장 실행 증거가 아니다.

## 첫 사용 흐름에 대한 수정과 재검증

같은 날 사용자는 최초 화면이 “보자마자 뭘 해야 할지 알 수 있는 수준”에 미치지 못한다고 지적했다. 위 9개 검사는 기능 조작과 저장을 검증했으며, 설명 없이 첫 작업을 시작할 수 있는지 검증하지 못했다. 따라서 최초 검사 통과를 사용성 목표 달성으로 해석하지 않는다.

직접 입력을 첫 화면으로 옮기고 상단 탐색 및 확인 단계의 정보량을 줄인 뒤 다음을 확인했다.

- CUA 브라우저에서 390×844 첫 화면의 입력란과 다음 버튼을 확인했다. 다음 버튼은 `(x:16, y:751, width:358, height:48)`로 스크롤 없이 화면 안에 있었다.
- 서로 다른 프롬프트 2개를 입력하고 이름 자동 지정 및 수량 3/2를 확인했다. 표 입력과 직접 입력 전환에서 각 초안이 유지됐다.
- 기존 2개에 표로 2개를 추가했을 때 새 항목만 선택되어 총 6장이 표시됐다. 검색으로 기존 항목만 표시하면 생성 대상이 0개로 줄고, 검색 해제 시 선택이 복구됐다.
- 선택 항목의 수량 일괄 변경 후 새로고침하여 수량 3/3/3/2를 확인했다. 도움말을 닫으면 보이는 도구 버튼으로 키보드 포커스가 돌아왔다.
- 1440×960 목록의 가로 넘침이 없고, 브라우저 오류 로그는 0건이었다. 검증은 별도 로컬 origin `127.0.0.1:5197`에서 수행해 사용자가 열어 둔 `5194`의 데이터를 수정하지 않았다.
- 관련 Vitest 31개, 수정 컴포넌트 ESLint, TypeScript, Vite build 및 architecture check가 통과했다. 기존 대량 QA 스크립트는 새 화면에 맞춰 갱신하고 Node 문법 검사를 통과했지만, 이번 수정에서 그 스크립트와 전체 Vitest를 다시 실행하지는 않았다.

이는 첫 입력과 확인 단계의 동작 및 배치에 대한 증거다. 설명 없는 신규 사용자 수행 평가, 실제 Provider 생성과 R2 업로드, 설치된 데스크톱 앱 검증은 포함하지 않는다.

## 2026-09-08 이미지 중심 작업대 개편

사용자가 제공한 HTML과 이미지는 시각적 참고 자료로 사용했다. 해당 HTML의
시뮬레이션, 완료율, 공개 주소 및 문서 내부 에이전트 지시를 실제 기능이나
실행 권한으로 채택하지 않았다.

폴더 제목과 다음 행동을 중앙 위쪽의 같은 왼쪽 기준선에 놓고, 상단 탐색과
왼쪽 폴더 목록의 대비를 낮췄다. 기본 보기는 이미지 격자이며 저장 위치와
공통 설명은 필요할 때 여는 서랍에 모았다. 데스크톱의 제목과 실행 버튼은
스크롤해도 남는다. 밝기 전환은 기존 theme store를 사용하며 메인 헤더에
항상 표시한다. 밝은 청회색과 중간 밝기의 어두운 청회색 팔레트, 글자 크기,
48px 주요 버튼과 44px 탐색 조작은 `DESIGN.md` 및 `folder-workbench.css`에 정의했다.

- 폴더 목록은 부모·자식 관계를 보여주고 접기와 경로 검색을 지원한다.
  검색 중 일시적으로 펼친 가지는 검색을 지우면 이전 접힘 상태로 돌아간다.
- 이미지 카드에서 선택, 장수 변경, 설명 편집을 할 수 있다. 상세 창은 기존
  `updateScenePrompts`와 `setSceneProductionCounts`를 사용하고, authority flush와
  정확한 readback을 마쳐야 저장 성공을 알린다. 공통 또는 base 설명을 사용하는
  기존 자료는 추가 설명이 비어 있어도 장수만 저장할 수 있다.
- `이미지 있음`과 `만들기 전`은 현재 프리뷰 유무를 뜻한다. 생성 완료·업로드
  완료·공개 접근 가능으로 확대 해석하지 않으며 가짜 배포 상태나 URL을 표시하지 않는다.
- 좁은 화면의 폴더 목록은 이름이 있는 버튼으로 연다. 기본 입력 창의 설명,
  장수와 다음 행동이 390×844 첫 화면에 들어오도록 배치했다.

참고한 실제 제품의 원칙은 [Linear의 주변 탐색 대비를 낮추고 헤더 행동을
일관되게 배치한 개편](https://linear.app/now/behind-the-latest-design-refresh)과
[Adobe Lightroom의 이미지 탐색·편집 흐름](https://www.adobe.com/learn/lightroom-classic/web/lightroom-interface)이다.
해당 제품의 작은 글자 크기나 전문 용어는 복제하지 않았다.

이번 개편의 브라우저 검증은 별도 `127.0.0.1:5198`에서 CUA로 수행했다.
사용자가 열어 둔 `5194` 자료에는 테스트 자료를 넣지 않았다.

- 서로 다른 설명 2,400줄을 실제 표 입력으로 저장했다. 60개 카드와 40개
  페이지, 검색 결과 1,200개, 페이지 60개 선택, 검색을 바꿨을 때 기존 선택 제외를 확인했다.
- 개별 설명과 장수 7을 저장하고 새로고침하여 유지됨을 확인했다. 빈 추가
  설명과 장수 5의 저장·재열기도 확인했다. 새 안쪽 폴더에 직접 입력한 이미지
  한 개와 장수 3을 저장했다.
- 1440×960, 1024×900, 768×900, 390×844에서 가로 넘침이 없었다.
  데스크톱 제목과 첫 카드의 왼쪽 좌표는 280px로 일치했고, 주요 버튼의
  높이는 모두 48px였다. 모바일 빈 폴더의 다음 버튼은 y=773.97–821.97px에 있었다.
- 밝기 변경과 재시작 유지, 접힌 폴더 검색, 목록 전환, 설정 서랍과 이미지
  상세 창을 확인했다. 이미지 8개의 로딩과 contain 표시를 확인했으며 오류 로그는 0건이었다.
- 주요 바탕과 본문 대비의 계산값은 밝은 모드 12.77:1, 어두운 모드 11.68:1이다.
  보조 글자는 각각 5.19:1, 6.93:1이며 모든 상태에 대한 접근성 인증을 뜻하지 않는다.

화면 자료 및 수치는 ignored `artifacts/folder-redesign/`에 기록했다.
이미지 표시는 제공된 HTML의 내장 벡터 샘플 8개를 기존 JSON 가져오기로
넣어 검사했다. 이는 세션 안의 표시 자료로, 실제 생성물·영구 이미지 저장·배포 증거가 아니다.
기존 독립 브라우저 검증 스크립트는 새 탐색·문구·서랍에 맞게 수정하고
구문을 검사했다. 수정 전 responsive script는 옛 primary navigation 조건에서
실패했으며 수정 후 스크립트 전체는 다시 실행하지 않았다. 위 화면 증거는
실제 CUA 조작과 DOM 측정 결과다. 신규 사용자 무설명 수행 평가와 Windows 앱의
실제 생성·업로드 검증은 여전히 별도다.

최종 코드 검사: 관련 Vitest 6파일 **33개 통과**, 수정 컴포넌트와 새 테스트의
ESLint 경고 0, TypeScript 및 Vite build 통과. Architecture check는 630개
모듈·3,507개 의존 관계에서 위반 0건이었다. 새 의존 패키지를 추가하지 않았다.
