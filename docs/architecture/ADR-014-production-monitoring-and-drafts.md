# ADR-014: 생산 결과 모니터링과 작업 초안 복구

- 날짜: 2026-09-09
- 상태: 첫 구현 단위. 전체 생산 작업과 Codex 이벤트 재호출은 미완료.
- 기준: `e6bf27f`, ADR-013, 사용자 요청과 `NAI_Blue_Agent_Production_Handoff.md`의 요구사항.
- 검증 기록: `docs/releases/evidence/agent-production-start-2026-09-09.json`.

## 사용자 흐름

사람과 에이전트는 같은 폴더·에셋을 편집하고 같은 생성 계획·승인·Queue를 이용한다.
사용자는 폴더에서 대상과 프롬프트·장수를 정하고 생성 계획을 확인한다. 생성 후에는
작업 기록에서 생성·저장·업로드 결과와 필요한 조치를 확인하고 폴더에서 프리뷰를 검토한다.
에이전트가 작업을 등록한 경우에도 이 경로를 그대로 사용한다.

입력하다 패널을 닫거나 다른 화면을 다녀와도 폴더별 초안을 복구한다. 검색·선택·보기·필터·
하위 폴더 포함·페이지·스크롤도 복구하며, 복구한 선택 범위는 기존 생성 계획 검토를 다시 거친다.
초안 복구는 생성 재개나 비용 승인이 아니다.

## 이번 구현

### 생성·저장·업로드를 같은 근거로 표시

`summarizeGenerationRun()`은 기존 `GenerationFulfillmentProjection`만 읽는다.
Queue, Provider 결과, OutputWriter, Artifact, Scene 연결, R2, 사람의 평가 저장소를 대체하지 않는다.

- `generation.get_run`의 기존 필드를 유지하고 `monitor`를 추가한다.
- `counts`는 전체 대상, 생성 확인, 저장 확인, 업로드 요청/확인, 기술적 충족, 실패, 불확실,
  취소, 건너뜀을 구분한다. 업로드 확인은 기존 R2 증거이며 추가 공개 URL 접속 검사가 아니다.
- `complete`는 1개 이상인 모든 항목의 생성·저장·선택한 업로드·연결 증거가 충족되고
  기존 전체 상태가 `delivered` 또는 `accepted`일 때만 참이다. Queue 성공만으로 완료를 만들지 않는다.
- `attention`, `nextAction`, `recoveryActions`는 현재 결과에서 확인할 조치를 안내한다.
  복구 조치에는 기존 정책·승인·명령을 그대로 사용한다. 불확실한 결과를 자동으로 다시 생성하지 않는다.
- `stateHash`는 항목 ID·상태·평가·문제의 내용 버전이다. 조회 시각만 바뀌어도 새 사건으로
  간주하지 않는다. 이는 이벤트 ID, 순서 번호, 수신 확인, 실제 진행 시각 또는 생존 신호가 아니다.
- 집계는 전체 항목을 사용하고 공개 개별 항목은 기존 100개 한도를 유지한다.

작업 기록 화면은 100장 이하의 선택한 묶음에 대해 화면이 보일 때 5초마다 위 결과를 갱신한다.
이 조회는 Queue의 1초 버전 조회와 별개여서 생성 이후의 업로드 완료도 반영한다. 같은 묶음의
조회는 겹치지 않으며 화면을 떠나거나 묶음을 변경한 뒤 도착한 결과는 적용하지 않는다.
기존 대규모 묶음은 상세 열기/수동 새로고침을 유지해 10,000개 작업 목록을 반복해서 전체 조회하지 않는다.
R2 DB v3는 기존 행을 유지한 채 Artifact ID 인덱스만 추가하며, 모니터링은 해당 이미지들의
업로드 기록만 조회한다. 출력 transaction ID가 모두 기록된 묶음은 해당 journal만 읽는다.
미기록 transaction이 있는 작업은 안전한 복구 판단을 위해 기존 전체 pending journal 탐색을
유지하므로, 100장 제한을 모든 저장소의 절대 조회량 상한으로 간주하지 않는다.
`작업 상태 복사`는 에이전트 조회와 같은 요약을 복사한다. 인증정보·프롬프트·이미지 바이트는 포함하지 않는다.

### 에이전트 없이도 입력과 작업 위치 복구

초안과 보기 상태는 장치 내 presentation 데이터이다. Scene·Folder·Queue의 권한 저장소와
분리된 localStorage 키를 사용하고, 실제 에셋 가져오기는 기존 Scene 저장 확인을 통과해야 한다.

- 입력 변경은 동기 저장하여 즉시 패널을 닫아도 보존한다. 저장 실패를 화면에 표시한다.
- 폴더별 초안은 최대 32개, 직렬화된 전체 내용은 200만 문자까지 보존한다.
  한도 초과 시 다른 폴더의 초안을 지우지 않고 저장 실패를 표시한다.
- 명시적인 `초안 버리기`를 제공한다. 가져오기에 성공한 경우 제출한 입력과 현재 저장된 입력이
  정확히 일치할 때만 제출한 모드의 내용을 비운다. 실패와 후속 편집은 보존한다.
- 보기 상태는 최근 32개 범위까지 보존한다. 스크롤은 쓰기 빈도를 제한하고 화면을 나갈 때 반영한다.
- 이 장치의 브라우저/WebView 저장 영역에 종속된다. 다른 장치와 동기화하거나 전체 백업에 포함하는 기능은 없다.

## Codex 호스트 검증 결과와 경계

2026-09-09 조사에서 npm Codex CLI는 0.153.2, 데스크톱 번들 바이너리는 0.153.4였다.
현재 NAI MCP는 명령 제출과 receipt 조회를 지원하며 이벤트 구독·발신 경로는 없다.

MCP 리소스 변경 알림은 호스트가 받는 JSON-RPC 알림이다. 모델에 새 입력을 전달하고 추론을
다시 시작하는 것은 별도 호스트 동작이다. 공개 Codex `LoggingClientHandler`의 일반 progress/
resource 알림 처리는 로그를 기록하며 이 경로에서 새 turn을 시작하지 않는다. 공개 main 소스와
설치 바이너리가 동일하다는 보장은 없으므로 이것을 설치본의 모든 기능 부재로 일반화하지 않는다.

- [MCP Resources 명세](https://modelcontextprotocol.io/specification/2025-11-25/server/resources)
- [Codex 일반 MCP 알림 처리](https://github.com/openai/codex/blob/main/codex-rs/rmcp-client/src/logging_client_handler.rs#L56)
- [Codex 별도 Plugin Runtime 이벤트 경로](https://github.com/openai/codex/blob/main/codex-rs/rmcp-client/src/event_notification_transport.rs#L109)
- [공식 Codex App Server 계약](https://developers.openai.com/codex/app-server/)

App Server를 소유한 클라이언트는 `thread/resume` 후 `turn/start`로 같은 저장된 작업에
입력을 보낼 수 있다. 그러나 외부 NAI watcher가 현재 데스크톱 소유 작업에 접속할 지원
endpoint와 동시 소유 계약은 이번 조사에서 확인하지 못했다. Windows의 관리 daemon 명령도
Unix 전용 오류를 반환했다. 일정 heartbeat를 이벤트 기반 무추론 대기의 증거로 대체하지 않는다.

따라서 `hostWakeupVerified: false`를 유지한다. 사용되지 않는 알림 전송기를 추가하지 않았으며,
모델 호출 0회·추론 토큰 증가 0·원래 작업 재호출은 측정 완료로 표시하지 않는다.

다만 실행한 뒤 원래 에이전트 작업이 자동으로 깨어난다는 약속은 호스트 검증을 통과해야 한다.
